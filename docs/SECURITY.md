# SupportGPT AI — Security Architecture & Baseline Controls

## 1. Security Philosophy & Principles
SupportGPT AI is architected from the first line of code with enterprise security invariants:
- **Defense-in-Depth**: Security controls are applied at transport, application, and database layers.
- **Fail-Closed Defaults**: In production or staging environments, missing or insecure configurations cause immediate startup termination rather than silent fallbacks.
- **AI as Proposal, Not Authority**: Any action generated by an AI model is formally categorized as an unverified proposal requiring deterministic policy verification or human approval.

---

## 2. Active Security Controls (Phase 00 Foundation)

### A. Secret Protection & Environment Isolation
- All sensitive credentials (passwords, tokens, keys) are strictly excluded from source control via `.gitignore`.
- Only safe, documented example files (`.env.example`) are checked in.
- Client-exposed variables are strictly restricted to `NEXT_PUBLIC_` prefixed keys; server-side secrets are never bundled into the client build.

### B. Production Invariant Validation (Pydantic v2)
The configuration engine enforces strict runtime validation:
- `DEBUG` mode is forbidden from being `True` in `staging` or `production` environments.
- Default development credentials (e.g. `supportgpt_dev_password`) are actively rejected in `staging` or `production`.
- Wildcard CORS (`*`) is rejected in `production`.

### C. Information Leakage Prevention & Error Sanitization
- API errors return standardized RFC 7807 envelopes.
- Internal exception stack traces, file system paths, and raw database queries are logged internally for engineering investigation but are completely redacted from client responses.
- Structured application loggers automatically scan extra fields and redact sensitive keys (`password`, `token`, `api_key`, `secret`, `authorization`).

### D. Request Correlation Tracking
- Every HTTP request is assigned or preserves an `X-Request-ID` UUID4 header.
- This identifier enables cross-system audit tracing across frontend, backend gateway, and database query logs without exposing internal session data.

### E. AI Action Safety Invariant
- The `AIActionProposal` model enforces an immutable boolean property `is_proposal: True`.
- Core services reject any attempt to execute an AI model output directly as an authorized transaction.

## 3. Active Security Controls (Phase 02 Authentication & Authorization)

### A. Argon2id Password Security & Constant-Time Verification
- **Argon2id Hasher**: Configured with memory cost 64MB (65536 KiB), 3 time iterations, and 4 parallel threads.
- **Timing Attack Neutralization**: When a non-existent account email is supplied to `/api/v1/auth/login`, the system executes an automated constant-time verification against a pre-computed dummy Argon2id hash (`_DUMMY_ARGON2_HASH`), eliminating timing-based email enumeration.
- **Zero Plaintext Credentials**: Plaintext passwords are validated in memory and immediately discarded. Password hashes are never returned in API payloads or serialized into logging contexts.

### B. Server-Side Revocable Session Lifecycle
- **Opaque Token Issuance**: Sessions issue 256-bit cryptographically secure random tokens (`secrets.token_urlsafe(32)`).
- **One-Way Token Hashing**: Databases store only the SHA-256 hash of the token (`session_token_hash`). If the database snapshot is compromised, active session tokens cannot be derived.
- **Transport Security**: Transported via `HttpOnly`, `SameSite=Lax` cookies (`SESSION_COOKIE_SECURE=True` enforced in staging/production) and optional `Authorization: Bearer <token>` headers.
- **Instant Revocation**: Calling `/api/v1/auth/logout` revokes the session record in the database immediately, invalidating any subsequent requests using that token.

### C. Multi-Tenant Authorization & Centralized RBAC
- **Untrusted Client Inputs**: Organization IDs, user IDs, or roles sent in request headers or bodies are NEVER treated as authorization authority.
- **Request Context Verification**: Every organization-scoped endpoint requires `OrganizationContext`, which validates caller authentication, active account status, target organization existence, and active membership status.
- **Least-Privilege Role Model**: Strict role hierarchy (`owner` > `admin` > `agent` > `viewer`).
- **Privilege Escalation Guards**:
  - `admin` cannot grant `owner` or `admin` roles, preventing unauthorized escalation or peer creation.
  - Demoting or revoking the final active `owner` in an organization is strictly blocked (`403 Forbidden`).
  - Revoked or suspended memberships immediately terminate all organization access.

### D. PostgreSQL Row-Level Security (RLS)
- **Database Engine Isolation**: PostgreSQL Row-Level Security (RLS) is enabled with `FORCE ROW LEVEL SECURITY` on all tenant-owned tables (`tickets`, `conversations`, `messages`, `attachments`, `ticket_events`, `customers`, `customer_identities`).
- **Transaction-Local Isolation**: Context is established via `SELECT set_config('app.current_organization_id', :org_id, true)`. The `is_local=true` flag guarantees that the session variable automatically resets on transaction commit or rollback, preventing tenant leakage across connection pool reuse.
- **Fail-Closed Default**: Queries with missing or unset tenant context return 0 rows and reject all inserts.

## 4. Active Security Controls (Phase 03 Ticket & Conversation Management)

### A. Direct-ID Attack Resistance & Anti-Enumeration
- Attempting to access an entity (ticket, conversation, message, customer, attachment, event) belonging to another organization yields `404 Not Found`, identical to a non-existent UUID.
- The API never responds with `403 Forbidden` or reveals whether a foreign UUID exists.

### B. Optimistic Concurrency Control (OCC)
- The `tickets` table uses a dedicated integer `lock_version` column.
- Concurrent updates with mismatched versions fail with `409 Conflict` (`CONCURRENCY_CONFLICT`), completely eliminating lost update race conditions between simultaneous support operators.

### C. Author Role Impersonation Prevention
- Ordinary agents are restricted to `author_type="agent"`.
- Submitting messages claiming `author_type="system"` or `author_type="ai"` requires administrative authority (`owner` or `admin`), preventing agent-level identity spoofing.

### D. Attachment Storage Key Redaction
- Attachment endpoints return public file metadata (`filename`, `content_type`, `size_bytes`, `scan_status`).
- Internal object storage paths (`storage_key`), cloud bucket names, and credentials are strictly excluded from API responses.

### E. Append-Only Audit Event Trail
- Ticket mutations atomically commit immutable `TicketEvent` records within the identical transaction.
- Historical events cannot be edited or deleted by normal API endpoints.

## 5. Inbound Webhook Verification & Cryptographic Secret Protection (Phase 04)

### A. Constant-Time HMAC-SHA256 Signature Verification
- Inbound webhooks are authenticated via HMAC-SHA256 evaluated over raw request bytes (`await request.body()`).
- Verification compares signatures using Python's `hmac.compare_digest` to eliminate timing side-channel attacks.
- Missing or invalid signatures terminate execution immediately with `401 Unauthorized` (`SIGNATURE_VERIFICATION_FAILED`).

### B. Replay Window Defense
- The webhook reception boundary enforces a maximum 300-second (5-minute) clock-skew window via timestamp headers (`x-supportgpt-timestamp`).
- Requests with timestamps outside this tolerance window are rejected with `400 Bad Request` (`TIMESTAMP_OUTSIDE_TOLERANCE`), neutralizing replay attacks.

### C. Payload Size Bounds & Content-Type Validation
- Strict 1 MB request body bounds (`MAX_WEBHOOK_PAYLOAD_BYTES = 1_048_576`). Payloads exceeding this limit fail fast with `413 Content Too Large` (`PAYLOAD_TOO_LARGE`).
- Rejects non-JSON media types with `415 Unsupported Media Type` (`UNSUPPORTED_MEDIA_TYPE`).

### D. Provider Secret Encryption at Rest
- Secrets are generated with high cryptographic entropy (`secrets.token_urlsafe(32)` prefixed with `whsec_`).
- Plaintext secrets are never stored in the database. Secrets are symmetrically encrypted at rest using AES-CTR mode stream cipher with per-secret random IVs derived from `settings.signing_secret_encryption_key`.
- Database storage includes `signing_secret_hash` (SHA-256) for lookups and `signing_secret_preview` for masked operator display (e.g., `whsec_abc...`). Plaintext secret values are never returned in read/list API contracts.

### E. Database-Level Deduplication & Digest Integrity
- Unique composite index `(organization_id, source_provider, external_event_id)` prevents duplicate records at the database engine level.
- Identical event IDs received with mismatched payload digests are flagged as integrity violations and rejected with `409 Conflict` (`PAYLOAD_DIGEST_MISMATCH`).

## 6. Knowledge Subsystem, Storage & Document Processing Security (Phase 05)

### A. Path Traversal Defense & Opaque Storage Keys
- Object storage keys never incorporate client-supplied filenames or arbitrary path segments. Keys follow the opaque template: `org_{org_id}/docs/{doc_id}/v{version_number}_{uuid}.bin`.
- `LocalStorageBackend` validates that storage keys contain no leading slashes, backslashes, drive letters, or directory traversal sequences (`..`).
- File paths are resolved and strictly verified against the storage root via `Path(resolved).is_relative_to(base_dir)`. Attempted path traversals raise `PathTraversalException` with HTTP 400 (`SECURITY_VIOLATION`).

### B. Format Signature Validation & Format Allowlist
- File validation rejects client-supplied extensions and MIME headers as untrusted. Files are validated using genuine binary signatures:
  - **PDF**: Verified against `%PDF-` signature.
  - **DOCX**: Verified as valid PKZIP containing `word/document.xml`.
  - **TXT / Markdown**: Decoded strictly as UTF-8/UTF-8-SIG without binary null bytes (`\x00`).
- Unknown extensions, executable binaries, archives, and shell scripts are rejected immediately with HTTP 415 (`UNSUPPORTED_MEDIA_TYPE`).

### C. Resource Bounds & Decompression Safety (Zip Bomb Defense)
- Enforces an upload ceiling of 20MB (`MAX_DOCUMENT_UPLOAD_BYTES = 20_971_520`).
- Archive-based documents (DOCX) are checked during decompression:
  - Total uncompressed size must not exceed 100MB (`MAX_UNCOMPRESSED_ZIP_BYTES = 104_857_600`).
  - Expansion ratio must not exceed 50x (`MAX_ZIP_COMPRESSION_RATIO = 50.0`).
- Violations raise `PayloadSizeLimitException` with HTTP 413 (`PAYLOAD_TOO_LARGE`).

### D. Untrusted Content Execution & Network Isolation
- Document parsers (`pypdf`, `python-docx`, text extractors) run without executing embedded macros, scripts, or active code.
- Parsers are prohibited from fetching remote URLs or following external references discovered in document content.
- Document content is never logged in full to application or system logs.

### E. Multi-Tenant Isolation & RLS Enforcement
- RLS policies are enabled and forced on `knowledge_bases`, `documents`, `document_versions`, and `document_chunks`.
- Composite foreign key constraints (`[knowledge_base_id, organization_id]`, `[document_id, organization_id]`, `[version_id, organization_id]`) guarantee relational integrity across tenant boundaries.
- Cross-tenant API lookups return HTTP 404 (preventing existence disclosure).

## 7. Security Boundary & Planned Milestones

| Security Milestone | Status | Description |
|---|---|---|
| **Multi-Tenant Row-Level Security (RLS)** | **Active (Phase 02–05)** | PostgreSQL RLS policies enforcing tenant isolation across tickets, events, sources, knowledge bases, documents, and chunks. |
| **Authentication & RBAC** | **Active (Phase 02)** | Argon2id password hashing, server-side revocable sessions, organization memberships, and role-based access control. |
| **Ticket & Conversation Authorization** | **Active (Phase 03)** | Direct-ID attack resistance, OCC conflict prevention, author impersonation blocks, and atomic event audit trails. |
| **Inbound Webhook Verification & Secrets** | **Active (Phase 04)** | Cryptographic signature validation (HMAC-SHA256), replay protection, AES-CTR secret encryption, and idempotent event processing. |
| **Safe Storage & Document Processing** | **Active (Phase 05)** | Path traversal guards, magic byte verification, zip bomb limits, and deterministic chunk provenance. |
| **Vector Store Tenant Isolation** | Phase 06 | Collection-level and payload-filtered tenant isolation in Qdrant vector database. |
| **Claim-Level Hallucination Guard** | Phase 07 | Automated decomposition of model completions into atomic claims, checking evidence grounding before delivery. |
| **Policy Approval Gates** | Phase 08 | Fine-grained intervention gates requiring dual authorization for sensitive actions. |
| **PII Redaction & Sanitization** | Phase 09 | Automated masking of customer Personally Identifiable Information in forensic trace logs. |
